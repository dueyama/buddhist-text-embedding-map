# Okyouリポジトリ立ち上げから論文公開準備までの制作プロセス

対象期間: 2026-06-01 17:33 JST から 2026-06-02 12:35 JST
対象リポジトリ: `Okyou/`（ローカルのプロジェクトルート）

## 位置づけ

本ドキュメントは、宗派別お経マップのリポジトリを立ち上げてから、実験コード、可視化、論文PDF、HTML論文、GitHub Pages公開準備に至るまでの制作プロセスをまとめるものである。

このプロジェクトは、[上山大信](https://sites.google.com/site/dueyama/)の指示にもとづき、Codex GPT-5.5 xhigh と反復的に実装・分析・文書化を進め、ChatGPT 5.5 Pro との査読形式のやり取りを通じて論文構成、先行研究整理、限界の記述を調整した、人文系データ解析論文制作のプロトタイプである。特に、OpenAI APIキーとChatGPT Proアカウントを持つ研究者が、この種の探索的研究をAI支援で半自動的に進めるための手順例として読めるようにすることを意図している。

ここでの主眼は、AIが単独で研究を行ったということではない。むしろ、人間が問い、資料選択、解釈、公開方針を決め、AIがコード実装、可視化、草稿化、レビュー対応、ローカル検証を高速に補助することで、人文学研究の探索的サイクルをどのように短時間で回せるかを試した点にある。したがって本ドキュメントは、完成物の報告であると同時に、他の研究者が真似できる作業手順の記録でもある。

## 前史: 既存ローカル実験フォルダ

このCodex作業は、完全な白紙から始まったものではない。プロジェクト開始時点のローカル作業環境には、上山大信が数年前に少し試した埋め込み関連の探索フォルダとして、`お経`、`埋め込みお経`、`埋め込みテスト` の三つが存在していた。

これらのフォルダは、当初の問題意識、すなわち「お経を埋め込みで比較できるのではないか」「阿弥陀経や宗派ごとの経典群を意味空間で眺められるのではないか」という問いの背景になった。ただし、それらは過去のローカル実験であり、公開・再現のための成果物としては扱わない。APIキーやraw本文が混在する可能性もあるため、初期のgit管理では `git add .` を避け、これらのフォルダは `.gitignore` で除外した。

今回のCodex支援作業では、過去フォルダに残る発想を受け継ぎつつ、公開可能なコード、図、論文、制作記録を `experiments/` と `docs/` に整理し直した。したがって、これら三つのフォルダは近く削除されても、本リポジトリの再現手順や公開物には影響しない。

## 再現の前提

同種のプロジェクトを再現する場合、少なくとも次の環境を前提とする。

- OpenAI APIキー: 埋め込み生成に使う。
- ChatGPT Proアカウント: 査読形式の相談、論文批評、改稿方針の検討に使う。
- Codex環境: ローカルファイル編集、スクリプト実装、検証、git管理に使う。
- git: 小さなコミット単位で研究過程を残す。
- Python 3: コーパス構築、embedding cache、図生成、viewer data生成に使う。
- 日本語TeX環境: PDFを再生成する場合に使う。HTML論文だけなら必須ではない。
- 対象本文の利用条件確認: SAT、J-SOKEN、84000など、本文提供元ごとの条件を確認する。

このプロジェクトでは、OpenAI APIで埋め込みを生成し、ChatGPT Proとの査読形式の往復で論文の問題設定、先行研究レビュー、限界の記述を鍛え、Codexでコード・図・文書・git管理を進めた。

## 道具準備も含めたAI支援

このプロジェクトで重要だったのは、AI支援が文章生成やコード生成に限られなかった点である。研究を進めるために必要な道具そのものも、対話しながら整えた。

実際に行った道具準備は次の通りである。

- OpenAI APIキーを `.env` から読む形にし、埋め込み生成スクリプトで使えるようにした。
- APIキーをgitに入れないため、`.env` と既存のAPIキー入りファイルを追跡対象から外した。
- embedding cache を導入し、同じ本文・同じモデルでは再課金しないようにした。
- SAT、J-SOKEN、84000などから取得したraw/processed本文を公開対象外にし、派生データだけを公開する方針にした。
- Pythonでコーパス構築、本文整形、チャンク化、埋め込み、図生成、viewer data生成を行うパイプラインを作った。
- ローカル静的ビューアを作り、`http.server` で配信してブラウザ確認できるようにした。
- 図入り論文PDFを作るため、ローカルに日本語TeX環境を準備した。
- 当初は軽量なTeX実行環境や大きなTeX配布の選択肢を検討し、最終的にBasicTeX + upLaTeX + dvipdfmx の構成で日本語PDFを生成した。
- PDFの日本語表示、図、表、参考文献、特殊文字をQuick Lookやブラウザで確認した。
- PDFだけでなくGitHub Pages上で読みやすいHTML論文を生成するため、TeXからHTMLへ変換するスクリプトを追加した。
- HTML論文では、付録に説明のある実装用語へ本文から飛べるようにし、数式はMathJaxで組版するようにした。
- GitHub Pages向けに、トップページ、公開版ビューア、HTML論文、PDF、制作プロセスHTMLを配置した。
- 公開用README、引用メタデータ、公開チェックリスト、`.nojekyll`、公開版データを整え、GitHub Pagesでそのまま読める構成にした。
- 公開版viewer dataから本文プレビューとローカルパスを除き、公開してよい派生情報だけにした。
- 変更ごとにgit commitし、`memory.md` に日時、検証、commit hashを記録した。

したがって、このプロジェクトの半自動性は「AIが論文本文を出力した」という意味ではない。むしろ、研究者が問いと判断を出し、AIが必要な道具をその場で作り、足りない環境を整え、検証し、成果物を公開可能な形へまとめるという、研究制作環境全体の半自動化である。最終的な公開準備、すなわちGitHub Pagesで読むためのHTML論文、公開版ビューア、プロセス文書、README、公開チェックリストの整備もCodexが実施した。

## 初期の問い

出発点は、「お経を埋め込みで比較したら、分類的な差が見えるのか」という問いだった。最初に検討したのは阿弥陀経の漢訳異本であり、同一または近い原文を異なる訳者が漢訳した場合、意味埋め込みでは近く出るはずだが、訳者や文体の癖はどのように見えるのか、という問題意識があった。

そこから問いは次のように拡張された。

- 阿弥陀経二訳は意味的に近く出るか。
- 訳者が同じ複数テキストは、意味以外のまとまりを示すか。
- 日本の代表的宗派が参照する経典群を地図化できるか。
- 教行信証のような日本撰述文献は、根拠となる浄土三部経とどのように重なるか。
- 点としての平均ベクトルだけでなく、チャンク分布の広がりや重なりを見られるか。
- 漢訳とチベット系英訳など、多言語でも「意味の同一性」が近傍として出るか。
- こうした作業を、Codexを用いた人文系データ解析論文制作の実験として記録できるか。

## フェーズ1: ローカル研究リポジトリの立ち上げ

最初に行ったのは、研究作業をローカルgitで管理できる形にすることだった。`AGENTS.md`、`.gitignore`、`memory.md` を作成し、作業ごとにJST日時、変更概要、検証、コミットhashを記録する方針を決めた。

この段階で重要だったのは、既存フォルダにAPIキーを含む可能性のあるnotebookやscriptがあったため、`git add .` を避け、安全な新規ファイルだけを明示的にstageする運用にしたことである。`.env`、raw text、embedding cache、legacy exploratory folders は公開・追跡対象から外すことにした。

同時に、以下の計画文書を作成した。

- `docs/kanbun-style-map-plan.md`
- `docs/sect-sutra-map-plan.md`
- `docs/results.md`

この時点で、阿弥陀経二訳比較の既存結果を `docs/results.md` に整理し、以後の実験結果を同じ場所へ追記していく流れができた。

## フェーズ2: 宗派別お経マップ v0 の実装

次に、`experiments/sect_sutra_map/` を新設し、宗派別お経マップのパイプラインを作成した。

基本構成は次の通りである。

- `manifest.json`: 対象テキストのメタデータ
- `common.py`: SAT/local text処理の共通関数
- `build_corpus.py`: 本文取得・整形
- `embed_texts.py`: OpenAI embeddings生成とcache
- `make_viewer_data.py`: 座標、類似度、重心、近傍データの生成
- `viewer/index.html`: ローカル静的ビューア

v0では、浄土系、法華系、真言系、禅系、華厳系の参照テキストを扱い、経典単位の平均ベクトル、宗派重心、チャンク近傍を表示できるようにした。初期結果では13 texts / 403 chunks、その後、訳者比較用の玄奘訳テキストを追加して15 texts / 433 chunksとなった。

この段階で、宗派分類を「正解ラベル」として当てるのではなく、「宗派が参照するテキスト群の配置を見る」ものとして位置づけたことが重要である。

## フェーズ3: 訳者比較と可視化の拡張

ユーザーから「同じ訳者の複数テキストはあるのか」という問いが出たため、訳者重心を追加した。鳩摩羅什、玄奘、不空など、複数テキストを持つ訳者について、宗派重心とは別に訳者重心を計算し、ビューアで表示できるようにした。

ここで見えてきたのは、単純な意味空間では、宗派、経典ジャンル、訳者文体が混ざりうるという点だった。つまり、埋め込み地図はただちに宗派分類器になるのではなく、意味、典拠、訳者、文体、宗派的受容が重なる探索空間として読む必要がある。

## フェーズ4: 論文形式への移行とPDF生成

可視化結果をもとに、日本語の論文草稿 `docs/sect-sutra-map-paper-draft.md` を作成した。その後、図入りPDFにするため、`docs/paper/sect-sutra-map-paper.tex` と図生成スクリプト `experiments/sect_sutra_map/make_paper_figures.py` を作成した。

日本語PDF生成では、最初に軽量なTeX環境を試し、その後 BasicTeX + upLaTeX + dvipdfmx の構成へ移行した。これにより、日本語本文、図、表、参考文献を含むPDFをローカルで生成できるようになった。

この段階で作成・更新された主な成果物は次の通りである。

- `docs/paper/sect-sutra-map-paper.tex`
- `docs/paper/sect-sutra-map-paper.pdf`
- `docs/figures/sect-sutra-semantic-map.png`
- `docs/figures/sect-sutra-similarity-heatmap.png`
- `docs/figures/amida-two-translation-comparison.png`

## フェーズ5: 出典クレジットと公開倫理の調整

教行信証本文について、ローカル由来の表示ではなく、浄土真宗本願寺派総合研究所の『浄土真宗聖典』聖教データベース由来であることを明示するように修正した。あわせて、`local` というユーザー向け表示を外し、出典URLと本文取得元の扱いを整理した。

この修正は、単なる表示の問題ではなく、公開時に本文提供元のクレジットと利用条件を尊重するための重要な工程だった。以後の公開準備でも、SAT、J-SOKEN、84000などのraw本文を再配布せず、派生的な座標、類似度、図、論文、コードを中心に公開する方針が維持された。

## フェーズ6: 点から分布へ

平均ベクトルを1点として描くだけでは、経典内部の広がりが見えないという問題意識から、チャンク分布の可視化を追加した。

追加された観点は次の通りである。

- テキスト平均ベクトルの2次元配置
- 各テキストのチャンク分布
- テキスト間チャンク近傍の混合
- overlap heatmap
- centroid similarity と chunk overlap の比較

この拡張により、教行信証が浄土三部経と完全に一致するわけではないが、部分的に重なりや橋渡しを持つという読みが可能になった。ユーザーの「教行信証は三部経を根拠にしているから、重なるはず」という解釈を、点の近さだけでなく、チャンク分布の重なりとして検討できるようになった。

## フェーズ7: 多言語パイロット

「チベットなど他言語のお経で比較可能なのか」という問いから、多言語比較のv0計画を作成した。その後、SATの漢訳『解深密経』T0676と、84000 Reading Room の Toh 106 英訳を用いたパイロットを実装した。

対照群として、金剛経、維摩経、般若心経、阿弥陀経などの漢訳を加え、84000英訳から見た最近傍の漢訳テキストが対応するT0676になるかを検証した。結果として、対応テキストが最近傍に出ることを確認し、埋め込みによる多言語意味対応の探索可能性が見えた。

ただし、この段階ではチベット語原文そのものではなく、チベット系英訳と漢訳の比較であるため、多言語比較としてはパイロットに留まる。

## フェーズ8: 親鸞と阿弥陀経二訳の典拠分析

親鸞がどの阿弥陀経をもとにしているのかという研究があるという話から、`experiments/shinran_amida_sources/` を新設し、親鸞文献と阿弥陀経二訳の参照関係を探索するパイロットを作成した。

ここでは、単純な意味類似度だけでなく、次の三つを分けて扱った。

- 明示的な引用・経名ラベル
- 康僧鎧訳・玄奘訳を示しうる訳語マーカー
- チャンク単位の意味的近傍

この分析により、親鸞文献と浄土三部経の関係を、宗派重心や平均ベクトルだけではなく、引用・語彙・意味チャンクの複数層で見る方向が加わった。

## フェーズ9: 査読形式の往復と論文改稿

論文草稿に対して、複数のレビュー文書が添付され、それぞれに対応した。

主な対応は次の通りである。

- 主張の過度な一般化を避け、予備的・探索的研究として表現を調整した。
- コーパス統計、PCA寄与率、top-k sensitivity、完全混合参照など、再現性と頑健性の説明を追加した。
- 図表ラベル、凡例、訳者名、法華経抜粋の説明を修正した。
- 著者名を最終的に[上山大信](https://sites.google.com/site/dueyama/)へ置換した。
- 先行研究レビューを追加し、Buddhist NLP、Buddhist DH、stylometry、parallel passage detection、cross-lingual semantic textual similarity との関係を明記した。
- 本稿の新規性を「仏教文献にembeddingを初めて適用した」ことではなく、「日本仏教の宗派別参照群、異訳、親鸞文献、チャンク分布、多言語パイロットを統合した探索地図」として再定義した。

この査読対応を通じて、論文は第2稿、第3稿、第4稿、第5稿相当へ進んだ。公開準備版のファイル名は番号付き稿ではなく、`docs/paper/sect-sutra-map-paper.tex` と `docs/paper/sect-sutra-map-paper.pdf` に統一した。

## フェーズ11: 直近のやり取りを公開可能な制作記録へ整理

公開準備の終盤では、論文本文だけでなく、論文がどのようにできていったかという対話的制作プロセスも公開対象にする方針になった。ここで重要なのは、チャットをそのまま転載することではなく、研究者の判断、AI支援の役割、査読形式の往復、実装上の修正を、第三者が再現しやすい手順として整理することである。

この段階で記録対象に加えたやり取りは次の通りである。

- ChatGPT 5.5 Pro による三層追加後の査読コメントを受け、`文体層` を `文体・語彙層`、`引用参照層` を `明示マーカー層` として、実装に即した表現へ改めた。
- `source-mixture map` は、論文本文では `三層参照源混合地図` と呼び、英語名は括弧内の補助名として残す方針にした。
- 三層参照源混合地図の方法節に、TF-IDFのfit範囲、参照源内最大類似度、softmax温度、平滑化幅、未対応チャンクを表す `その他` カテゴリ未導入の限界を追記した。
- 図1と図12の表記を、本文の用語に合わせて再描画した。
- 謝辞では、ユーザーの希望により、`ChatGPT 5.5 Pro xhigh を査読者役として` 用いたという記述を保持した。
- 付録「用語・モデル・ツール」にある語は、HTML論文の本文中の初出から付録項目へリンクするようにした。
- HTML論文の数式がTeX記法のまま見えていたため、MathJaxを導入してブラウザ上で数式として表示するようにした。
- 英語版論文については、日本語版が完成した後に、単なる直訳ではなく、英語本文に漢字原題・T番号・必要な原文名を初出で添える方式で作る方針を確認した。

このフェーズは、AI支援研究の公開記録として特に重要である。研究成果だけを見ると、図表と論文が最初から整っていたように見える。しかし実際には、研究者が「これは変だ」「この表現は残したい」「この図は読みにくい」「英語版はどう扱うべきか」といった判断を逐次与え、Codexがそれをコード、図、HTML、PDF、git履歴、制作プロセス文書へ反映していった。この反復こそが、本プロジェクトの再現可能なワークフローである。

## フェーズ12: 最終段階査読と出版品質チェック

その後、最終段階査読として `sect-sutra-map-final-stage-review.md` が提示された。判定は、内容面では「ほぼ投稿可能」「再査読不要相当」であり、残る作業は用語統一、字形確認、PDFメタデータ、参考文献体裁などの最終校正とされた。

この査読を受け、Codexは次の修正を行った。

## 半自動ワークフローとして真似できる点

このプロジェクトから、同種の人文系データ解析研究で真似しやすい手順は次のように整理できる。

1. まず、研究の問いを粗く置く。
   例: 異訳は埋め込み上で近く出るか、宗派の参照経典群は地図化できるか。

2. 対象テキストをmanifestにする。
   id、title、source、source_url、分類ラベル、訳者、時代、注記を構造化しておく。

3. 本文取得・整形・チャンク化をスクリプト化する。
   raw本文は公開しない前提でcacheし、公開物には派生結果だけを残す。

4. OpenAI APIで埋め込みを作り、cacheする。
   同じ本文・同じモデルでは再課金しないようにする。

5. 平均ベクトルだけでなく、チャンク分布も見る。
   テキストを一点に潰すと見えない広がりや重なりが、解釈上の手がかりになる。

6. 静的ビューアを作る。
   研究者が結果を眺めながら問いを変えられるようにする。

7. 結果ログを残す。
   入力、モデル、チャンク数、主要数値、解釈、未検証点を `docs/results.md` に記録する。

8. 論文草稿を作り、ChatGPT Proで査読形式のコメントを得る。
   Codexでコメント対応、図表修正、追試、PDF/HTML生成を行う。

9. 対話的な改稿過程を公開向けに要約する。
   チャットをそのまま公開するのではなく、研究者の判断、AIの作業、検証、残った限界を制作記録として整理する。

10. 公開前に出典と秘密情報を確認する。
   APIキー、raw本文、ローカルパス、利用条件に問題がないか確認する。

11. GitHub PagesでHTML論文とビューアを公開する。
    PDFも残しつつ、WebではHTMLを主導線にする。
    公開前には、AI支援で生成した公開版データからraw本文、ローカルパス、APIキーが除外されていることを確認する。

この一連の流れは、対象が仏教文献でなくても、古典文学、歴史資料、思想文献、法令、書簡、日記、翻訳比較などに応用できる。

## このプロトタイプが示したこと

第一に、CodexとOpenAI APIを使うことで、問いの変更に応じて、実験コード、可視化、論文草稿、査読対応、公開準備を連続的に進められることが示された。特に、人文学の探索的研究では、最初から固定された仮説検証ではなく、可視化を見ながら問いを変えていくことが多い。このプロジェクトでは、その変化が `memory.md` とgit履歴に残る形で進んだ。

第二に、意味埋め込みは、宗派分類そのものの正解を与えるものではないが、参照テキスト群、異訳、訳者、チャンク分布、多言語対応を同じ画面で探索するための地図として有効である可能性がある。

第三に、論文制作においては、AIが文章を整えるだけでは不十分であり、出典クレジット、本文再配布の制限、査読コメントへの応答、過度な主張の抑制、再現性の記述が必要である。このプロジェクトでは、それらを短い反復で追加・修正していった。

第四に、ChatGPT 5.5 Proとの査読形式の往復は、Codexによる実装・改稿作業に対して、外部レビューに近い圧力を与える役割を果たした。これにより、単なる実験メモから、先行研究と限界を備えた予備論文へ近づいた。

## 残る課題

- GitHub repository URLが確定したら、`CITATION.cff` の `repository-code` を更新する。
- コード、論文、図のライセンス方針を決める。
- SAT、J-SOKEN、84000など各提供元の利用条件を再確認し、公開ページ上のクレジットを必要に応じて増補する。
- チャンクサイズ依存性、自然単位チャンク化、本文正規化、異体字・句読点処理を検証する。
- 意味マップ、文体マップ、引用参照マップを分離し、それぞれの特徴量で比較する。
- チベット語原文・サンスクリット・パーリを含む多言語比較へ拡張する。
- 親鸞文献と浄土三部経の関係について、既存研究の典拠論と照合する。
- HTML論文とPDF論文を、公開後のGitHub Pages上で再確認する。
- 日本語版論文が完成した後、英語版HTML/PDFを別ディレクトリで作成する。英語版では英語本文を主とし、初出に漢字原題、T番号、主要資料名を添える。

## まとめ

このリポジトリの立ち上げから公開準備までの作業は、仏教文献の意味埋め込み分析であると同時に、AI支援による人文学研究制作の実験だった。[上山大信](https://sites.google.com/site/dueyama/)が問いと判断を与え、Codex GPT-5.5 xhigh がコード、図、文書、検証、git管理を伴走し、ChatGPT 5.5 Pro との査読形式のやり取りが論文の構成と位置づけを鍛えた。

その結果、単発の分析メモではなく、再現用コード、可視化、論文、査読対応、公開チェックリスト、GitHub Pages向けHTMLを含む、小さな研究リポジトリとしてまとまった。OpenAI APIとChatGPT Proを持つ研究者であれば、この構成をひな型として、別の人文学資料にも応用できる。
